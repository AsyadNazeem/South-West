# Bulk product import operations

The import upload is temporarily held in process memory. Each application process accepts at most 20 pending uploads and 100 MB total, each workbook is limited to 10 MB and 500 data rows, and uploads expire after 30 minutes. A cleanup timer removes expired records. Import tokens are bound to the uploading admin; confirmation uses an in-process lock and stores its outcome so a repeated confirmation is idempotent. A retry request processes only rows whose previous database transaction failed.

This temporary store is process-local. The endpoints must be routed to the same application worker for the lifetime of the upload. Restarts clear outstanding uploads and results. Multi-worker deployments without sticky routing cannot share preview tokens; use a shared ephemeral store if that deployment model is required.

Each product must have at least one variant. The Products sheet includes Unit of Measure, Warranty, Condition, and required Shipping Weight (kg). Unit and warranty choices are loaded from active database records each time a template is generated; Condition uses the values supported by the product registration form. Shipping weight must be a positive number with at most three decimal places and is stored in kilograms. There is no separate Shipment field.

The Products sheet also includes the manual Mark as New Yes/No value. Blank values mean No. This is saved to the parent product's `is_new` field and affects only the NEW! badge; customer visibility remains controlled by variant stock history.

The Variants sheet includes an optional QuickBooks Item Code, stored on the individual variant's existing `qb_item_code` field. It is treated as text so alphanumeric codes and leading zeros are retained. No schema change is required.

Variants also include Reorder Quantity, stored in the existing `inventory_stock.reorder_quantity` field (DECIMAL(15,3)). Zero is valid; values must be non-negative and have at most three decimal places. A stock location is required when either Stock Quantity or Reorder Quantity is positive. Reorder-only rows create the variant/location stock settings with zero on-hand and do not create an opening stock movement. Active inventory locations are included in the template reference list, matched by name or code, and resolved again from the retained workbook during import confirmation.

The workbook contains only the Products and Variants entry sheets; after importing, admins add or edit each variant's configured specifications in product administration. A legacy `Variant Specifications` sheet is rejected so its data is not silently ignored. Opening stock is recorded against the variant as a positive `goods_receipt` movement with `reference_type: bulk_product_import`, in the same transaction as the product and relationships. Product codes are generated by `itemCodeService`; variant SKUs are generated by the existing `generateVariantSku` rule. Workbook rows use product and variant names to link related information.
