# South West SEO and Google crawl health audit

25 November 2026 · Repository revision `d884353` · Investigation only

## 1. Executive summary

Prioritize the reported server errors and the storefront's URL handling. One product drawn from the live sitemap redirected to a URL whose canonical pointed back to the redirect. The shop responded on four protocol/hostname combinations. A missing product and a missing image both returned a successful HTML document. These are reproducible serving issues. The historical 5XXs warrant prompt investigation, but the available evidence does not attribute them to any particular controller, host or cause.

Keep public catalog JSON and product media crawlable. The browser uses these resources to display products and categories, including on product pages with build-generated metadata. The API robots.txt 404 permits crawling under Google's rules. Blocking the API to reduce its request count could remove content from Google's rendered view.

## 7. Findings that represent normal behaviour

- The only source robots file found was `Frontend/Customer/public/robots.txt:1–11`, with a copy in customer dist. For all agents it allows / and disallows the prefixes /account, /cart, /checkout, /login, /register, /set-password and /verify-email. It declares the HTTPS apex sitemap. No CSS, JS, product path or uploads rule is blocked there. Private-page crawl controls and access control serve different purposes. Blocked pages may never expose their client noindex to Google.
- API Express registers the root JSON response, public routes and uploads, with no robots handler or catch-all storefront rewrite (`Backend/src/app.js:145–150,216–255`). A 404 is consistent with this architecture. Google interprets robots 404 as unrestricted crawling for that origin. Retain apex rules, consolidate www/HTTP at the storefront, and leave API robots absent or publish a simple permissive file if operational clarity is desired. Preserve access to public store data and uploads. Keep private/admin routes authenticated irrespective of robots. A robots change alone cannot address a connectivity or 5XX incident. [Google robots.txt specification](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec)
- A single permanent redirect for a genuinely moved URL is healthy. C1 is an avoidable redirect from the preferred URL itself. The audit cannot apportion the historical 4% between these cases. The www count being close to the approximate redirect count does not establish a relationship.
- A 304 requires a conditional request and a matching validator. Immutable versioned assets, new builds, random catalog seeds and frequently changing offers can all reduce observed 304s. The reported rate alone establishes no caching defect.
- Refresh-heavy crawling can be appropriate for a stable range with changing stock/prices. Track time from publish to sitemap inclusion, first verified fetch and indexing for newly launched items. Use the 417 ms mean as a baseline, then prioritize routes with sustained high tail latency, failures or material rendering delays.

## 8. Root cause analysis and diagnostic boundaries

**API crawl path.** The build embeds the API base in storefront code (`.cpanel.yml:4`, `Frontend/Customer/index.html:17–40`, `Frontend/Customer/src/services/api.js:4–10`). Home loads banners, sections, categories, filters and product pages (`Frontend/Customer/src/pages/Home.vue:151,260,318–335,480,634`). The banner promise is reused on success. Shop loads category metadata then products on mount, even on the unfiltered shop (`Frontend/Customer/src/pages/footer/StoreListing.vue:195–219`). Product details first fetch by public UUID, then fetch variants by internal ID, then reviews. Wishlist has a session guard (`Frontend/Customer/src/pages/ProductDetails.vue:310,340–346,1522–1549,1638–1665`). Theme and contact resources also participate. Product snapshot fallback is attempted after a transient failure. Confirmed absence is handled separately. Header search requests the unpaginated catalog after user input of at least two characters (`Frontend/Customer/src/layouts/AppHeader.vue:196–212`), which is evidence of potential shopper cost, not an automatic Googlebot request.

**Documents versus resources.** All live sitemap locations were on the apex. Product canonicals, offer URLs, breadcrumbs and card links are storefront destinations. All 123 product schemas in the existing local build pointed their image field at the API host. Public uploads therefore have an explicit discovery path independent of XHR. API also serves HTML at /api/social-preview/product/:slug with a storefront canonical and a link back (`Backend/src/routes/socialPreviewRoutes.js:8–10`, `Backend/src/controllers/socialPreviewController.js:121–150,162–167`). No storefront link to that endpoint was found in customer source. A JSON file-type count does not identify an indexed document or tell which page initiated the request.

**Failure boundaries.** Product list/filter/related/variant handlers catch failures and emit 500 (`Backend/src/controllers/storeProductController.js:688–699,871–880,942–954,1215–1227`). Category errors are logged with DB error details and return 500 (`Backend/src/controllers/storeCategoryController.js:62–72`). Missing/ineligible items on related/variant routes have explicit 404s, malformed requests can hit 400, and an empty catalog lookup can return a successful list (`Backend/src/controllers/storeProductController.js:73–81,136–141,294–301,730–757,965–990`). None demonstrates a historical null-reference exception. A missing category parent is guarded (`Backend/src/controllers/storeCategoryController.js:43–54`). DB authentication or theme-sync failure before listen can leave an upstream without an application listener. CORS rejection occurs before request logging and uses an Error for an unapproved Origin. No-Origin requests pass. These are concrete failure paths, not identified production incidents.

**Timeouts, dependencies and logging.** The customer Axios deadline is 15 seconds. Build fetches use 20 seconds for listing and 15 for variants. A client timeout is not proof of an HTTP 504. No explicit pool tuning in the inspected DB constructor. Auth middleware can return 401 or 500 (`Backend/src/middleware/customerAuthMiddleware.js:21–39,91–104`), and auth/review/guest-checkout paths have dedicated limiter middleware. The store product GET route chain has neither auth nor a limiter (`Backend/src/routes/storeProductRoutes.js:14–25`). Inspect any hosting-layer limits for 429 separately. Public catalog reads depend on database and media storage. Google Fonts is referenced by the frontend (`Frontend/Customer/index.html:90–96`), but an external font failure would not establish a local 5XX. Request logger records method and URL before dispatch, without final status, elapsed time or crawler identity (`Backend/src/app.js:138–143`). No production access/error logs or verified crawler traces found. For storefront static failures inspect LiteSpeed/vhost/deploy logs as well as API process and DB logs.

## 11. SEO and business impact

A failed catalog resource can affect multiple storefront pages and customers even when each HTML document returns 200. Conversely, cutting API traffic indiscriminately could remove current prices, availability, photos or category links from rendered pages. Conflicting canonicals, stale offers and successful missing pages affect different stages of search and merit separate measurements. No traffic loss, missed revenue, indexing penalty or affected SKU count can be quantified from these aggregates.

## 12. Recommended solutions

Restore a single final URL for each public page, implement authoritative missing-resource responses, and align product metadata with current catalog identity. Give priority listing pages meaningful initial content and linkable pagination. Share repeated public contact fetches. Preserve the existing asset caching and public media access. Make decisions on API indexing headers, category landing pages, SQL changes or cache TTLs only after verifying their respective evidence in S1–S5.

## 13. Risks and dependencies

The last column of each issue register records implementation risk and complexity. The highest-risk dependency is product lifecycle state: the serving layer must distinguish a deleted item, a just-published item and an unavailable catalog. Test with fixtures for each before changing status codes or enabling cleanup. Coordinate redirect, sitemap, structured data and internal-link changes in the same release. Verify stock and price freshness before reusing product responses; contact information can use an independent cache policy.

## 15. Post-implementation verification plan

1. Use staging fixtures for an active product, new product, renamed slug, unavailable variant, retired item, nonexistent UUID, unknown page and absent asset. Compare first status, each Location, final URL, MIME type and canonical across protocol, host, slash and query variants. Preserve attribution parameters where appropriate.
2. Diff sitemap URLs against eligible catalog IDs and deploy manifest after publish, rename and deletion. Verify location uniqueness and status. If lastmod is added, change a price/description and confirm only materially updated URLs advance. Monitor publication-to-discovery delay for a cohort.
